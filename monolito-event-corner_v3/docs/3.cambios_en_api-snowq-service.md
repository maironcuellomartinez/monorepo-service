  Reintentos hacia ServiceNow — quién controla qué

  La cadena tiene tres responsables distintos, cada uno dueño de una sola decisión:

    api-gateway          → decide la PRIORIDAD de cada request
    api-snowq-service     → decide, a partir de esa prioridad, CUÁNTOS reintentos y con qué backoff
    micorner (reconciler) → decide, ante un FAILED, si vale la pena pedirle a snowq que reintente

  ─────────────────────────────────────────────────────────────────────────
  1. api-gateway fija la prioridad (no el tipo de request)

  apps/api-gateway/src/outbound/servicenow/servicenow-outbound.controller.ts

    buildIncidentBody()  → priority: 2 (MEDIUM)
    buildRequestBody()   → priority: 1 (LOW)

  Ese valor viaja en el payload hacia snowq. api-snowq-service NO lo recalcula:
  snow-request-processing.service.ts:72,114 pasa dto.priority directo a
  snowRequestService.create(), tal cual llegó.

  ─────────────────────────────────────────────────────────────────────────
  2. api-snowq-service traduce prioridad → reintentos y backoff

  api-snowq-service/src/common/enum/request-priority.enum.ts

  Máximo de reintentos por prioridad (RequestPriorityUtils.getMaxRetries):
    CRITICAL → 20 reintentos
    HIGH     → 12 reintentos
    MEDIUM   →  8 reintentos   ← la que usan los incidentes
    LOW      →  5 reintentos   ← la que usan las requests / service-catalog

  Backoff exponencial + jitter entre reintentos (RequestPriorityUtils.getRetryDelay):
    delay = clamp(base × 2^retryCount, techo) × jitter (50–100% del valor calculado)
    Base:  CRITICAL/HIGH/MEDIUM = 30s  ·  LOW = 60s
    Techo: CRITICAL = 2min · HIGH = 5min · MEDIUM = 10min · LOW = 30min

  Ejemplo MEDIUM (incidentes): intento0 15–30s → intento1 30–60s → intento2 60–120s
  → intento3 120–240s → intento4 240–480s → intento5+ 300–600s (techo)

  Cuando se agotan los reintentos de esa prioridad, snow-request.service.ts:markAsRetry()
  marca el registro como FAILED en la tabla snow_requests.

  ─────────────────────────────────────────────────────────────────────────
  3. El reconciler del micorner reacciona al FAILED

  apps/micorner/src/infrastructure/jobs/micorner-reconciler.job.ts — isFatalError(lastError)
  clasifica el motivo antes de decidir si reintentar:

  ┌────────────────────────────────────┬────────────────────────────────────────────────────┐
  │           Tipo de FAILED           │                       Acción                       │
  ├────────────────────────────────────┼────────────────────────────────────────────────────┤
  │ Error temporal (SN caído, timeout) │ retrySnowqEntry → snowq vuelve a QUEUED            │
  ├────────────────────────────────────┼────────────────────────────────────────────────────┤
  │ Error fatal (auth rota, 401/403)   │ Limpia correlationId + log de error (no reintenta) │
  └────────────────────────────────────┴────────────────────────────────────────────────────┘

  snow-request-queue.controller.ts expone lastError en el status para que el reconciler
  pueda distinguir ambos casos vía GET /snow-requests/{correlationId}.

  ─────────────────────────────────────────────────────────────────────────
  Nota: request-type.enum.ts no define prioridad ni reintentos por tipo de request.
  La prioridad depende únicamente de quién llama a snowq (api-gateway), no del tipo
  (incident, change_request, etc.) — ver punto 1.
