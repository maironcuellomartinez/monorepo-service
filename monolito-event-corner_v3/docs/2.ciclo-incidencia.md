 Cómo funciona realmente el proceso (con lo que descubrimos)

  ---
  Lo que hace api-snowq-service internamente

  Cuando un ticket entra a la cola async, snowq ya tiene su propio mecanismo de reintento:

  - Éxito → estado DELIVERED, guarda sysId + number
  - Error temporal (SN caído: 5xx, 408, 429) o circuit breaker abierto → vuelve a QUEUED con backoff exponencial por prioridad:
    - MEDIUM/LOW priority: espera 30–60 segundos entre intentos
  - Agota los 3 reintentos internos → estado FAILED (su DLQ lógica)
  - Error fatal (4xx, auth) → FAILED directo sin reintentos

  ---
  Flujo completo corregido

  CREACIÓN
  Incident → snowq (inmediato o encola)
    ├─ INMEDIATO: sysId + number → guardados ✓
    └─ DEFERRED: correlationId guardado en incident

  SNOWQ INTERNAMENTE (invisible para el monolito)
    Worker (cada 500ms) procesa la cola con prioridad
    Si SN está caído:
      intento 1 falla → espera 30s → intento 2 → espera 30s → intento 3
      todos fallan → FAILED

  RECONCILER (cada 30s) pregunta al gateway por el estado
    ├─ QUEUED / IN_PROGRESS → espera próximo ciclo
    ├─ DELIVERED → guarda sysId + number, borra correlationId ✓
    └─ FAILED → llama POST /reconcile/:correlationId/retry en snowq
                 snowq resetea retryCount=0 → vuelve a QUEUED
                 correlationId se MANTIENE → reconciler lo sigue monitoreando
                 Si el retry también falla (snowq down) → borra correlationId → orphan

  ORPHAN RECOVERY (cada 10 min, solo si SNOW_ORPHAN_RECOVERY_ENABLED=true)
    Casos donde llega aquí:
      1. Primera creación falló antes de tener correlationId (outbox agotó reintentos)
      2. Reconciler intentó retry en snowq pero snowq estaba caído
    Acción: re-encola en snowq async → nuevo correlationId → reconciler retoma ✓

  ---
  Diferencia clave respecto a lo que creías

  Lo que pensabas: "snowq re-encola automáticamente cuando SN cae, y el monolito debería simplemente consultar"
  → Correcto, pero parcialmente. Snowq reintenta 3 veces. Si SN está caído más de ~90 segundos, pasa a FAILED y deja de reintentar solo.

  Lo que hace ahora el reconciler en FAILED:
  → No borra el correlationId. Pide a snowq que retome el mismo entry (retryCount=0 → QUEUED). Es como si nunca hubiera fallado. El mismo correlationId sigue activo y el reconciler lo sigue monitoreando
  normalmente.

  El orphan job es solo el último recurso cuando snowq mismo no está disponible para aceptar el retry.
