 Cómo funciona realmente el proceso (con lo que descubrimos)

  > Actualizado 2026-07-31 tras el remodelado `Incident`/`Request` → `Appointment` en el monolito. Las referencias a "incidentes"/"requests" en la sección de `api-snowq-service` de más abajo son las **prioridades/tipos de ticket SN** propios de ese servicio (`RequestType`: `incident`, `sc_req_item`, `sc_task`, etc.) — no tienen relación con las entidades `Incident`/`Request` que el monolito eliminó; ese servicio no cambió.

  ---
  Lo que hace api-snowq-service internamente

  Cuando un ticket entra a la cola async, snowq ya tiene su propio mecanismo de reintento,
  gobernado por la PRIORIDAD del request (fijada por api-gateway, no por api-snowq-service —
  ver detalle completo en docs/3.cambios_en_api-snowq-service.md):

  - Éxito → estado DELIVERED, guarda sysId + number
  - Error temporal (SN caído: 5xx, 408, 429) o circuit breaker abierto → vuelve a QUEUED con
    backoff exponencial + jitter (base 30s para incidentes/MEDIUM, techo 10min)
  - Agota los reintentos de su prioridad (8 para incidentes/MEDIUM, 5 para requests/LOW) →
    estado FAILED (su DLQ lógica)
  - Error fatal (4xx, auth) → FAILED directo sin reintentos

  ---
  Flujo completo corregido

  CREACIÓN
  Appointment → snowq (inmediato o encola)
    ├─ INMEDIATO: sysId + number → guardados en el ServiceNowTicketLink ✓
    └─ DEFERRED: correlationId guardado en el ServiceNowTicketLink

  SNOWQ INTERNAMENTE (invisible para el monolito)
    Worker (cada 500ms) procesa la cola con prioridad
    Si SN está caído: reintenta con backoff exponencial + jitter hasta agotar los
    reintentos de su prioridad (8 para incidentes) → FAILED

  RECONCILER (cada 30s) pregunta al gateway por el estado
    ├─ QUEUED / IN_PROGRESS → espera próximo ciclo
    ├─ DELIVERED → guarda sysId + number, borra correlationId ✓
    ├─ FAILED + error TEMPORAL (SN caído, timeout, circuit breaker)
    │   → llama POST /reconcile/:correlationId/retry en snowq
    │      snowq resetea retryCount=0 → vuelve a QUEUED
    │      correlationId se MANTIENE → reconciler lo sigue monitoreando
    │      Si el retry también falla (snowq down) → borra correlationId → orphan
    └─ FAILED + error FATAL (401/403/404/422/400, auth/validation)
        → borra correlationId directo, sin pedir retry → orphan
        (reintentar un payload/auth inválido no cambia el resultado)

  ORPHAN RECOVERY (cada 10 min, solo si SNOW_ORPHAN_RECOVERY_ENABLED=true)
    Casos donde llega aquí:
      1. Primera creación falló antes de tener correlationId (OutboxWorkerService agotó
         sus 5 reintentos, ~2.5 min)
      2. Reconciler recibió FAILED fatal, o el retry temporal también falló en snowq
    Acción: re-encola en snowq async → nuevo correlationId → reconciler retoma ✓

  ---
  Diferencia clave respecto a lo que creías

  Lo que pensabas: "snowq re-encola automáticamente cuando SN cae, y el monolito debería
  simplemente consultar"
  → Correcto, pero parcialmente. Snowq no reintenta indefinidamente por su cuenta: agota
  los reintentos de su prioridad (8 para incidentes, con backoff exponencial — bastante
  más que unos segundos) y ahí pasa a FAILED, dejando de reintentar solo.

  Lo que hace el reconciler en FAILED depende del motivo:
  → Temporal (SN caído): NO borra el correlationId. Pide a snowq que retome el mismo
    entry (retryCount=0 → QUEUED). Es como si nunca hubiera fallado — el mismo
    correlationId sigue activo y el reconciler lo sigue monitoreando normalmente.
  → Fatal (auth rota, payload inválido): SÍ borra el correlationId de una — reintentar
    no va a arreglar un 401 o un payload mal formado. Pasa directo a huérfana.

  El orphan job es el último recurso: cuando snowq mismo no está disponible para aceptar
  el retry (caso temporal), o cuando el error era fatal desde el vamos.
