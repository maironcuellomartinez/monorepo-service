## Patrones de diseno

### Bulkhead en 3 capas

```
┌─────────────────────────────────────────────────────────┐
│  Capa 1: HTTP Bulkhead (middleware)                     │
│  Protege: todo el servidor HTTP                         │
│  Limite: 50 concurrentes, 100 en cola                   │
│  Excluye: /health/status                                │
├─────────────────────────────────────────────────────────┤
│  Capa 2: OAuth Bulkhead (guard)                         │
│  Protege: POST /oauth/token (bcrypt)                    │
│  Limite: 3 concurrentes, 5 en cola, timeout 5s          │
│  Objetivo: evitar DoS por bcrypt                        │
├─────────────────────────────────────────────────────────┤
│  Capa 3: Gateway PQueue + Circuit Breaker (service)     │
│  Protege: llamadas salientes al api-gateway             │
│  Limite: HP 10 concurrencia, LP 5 concurrencia          │
│  Circuit breaker: 50% error, 30s reset                  │
└─────────────────────────────────────────────────────────┘
```

### Refresh token rotation

```
POST /oauth/refresh
   │
   ├─ 1. Verificar firma JWT del refresh token
   ├─ 2. Buscar en BD por hash del jti
   ├─ 3. Comparar hash con bcrypt
   │
   ├─ Si NO coincide → REUSE ATTACK
   │   └─ Revocar TODOS los tokens del cliente
   │
   ├─ Si expirado → 401
   │
   ├─ Si valido:
   │   ├─ Revocar token actual (revokedAt = now)
   │   ├─ Emitir nuevo access_token
   │   └─ Emitir nuevo refresh_token
   └─ Devolver nuevos tokens
```

### Guard compuesto (AdminOrAccessGuard)

```
GET /v1/requests/*
   │
   ├─ 1. ¿Cookie admin_session?
   │   ├─ Si → verificar JWT admin → inyectar adminUser
   │   └─ No → continuar
   │
   ├─ 2. ¿Bearer token?
   │   ├─ Si → verificar JWT auth → inyectar externalClient
   │   └─ No → 401
   │
   └─ 3. Si ninguno → 401
```

## Decisiones arquitectonicas

### Autenticacion local vs OAuth externo

Se eligio **JWT local + MySQL** sobre OAuth introspection externa porque:

- Menos dependencias de red (no requiere llamar a un servidor OAuth externo en cada request)
- Latencia menor (verificacion local vs HTTP round-trip)
- Control total sobre el ciclo de vida de los tokens
- La feature branch con OAuth introspection quedo descartada

### Duracion configurable del token por cliente

Cada cliente puede tener su propia duracion de access token (entre 1h y 7 dias), almacenada en `tokenExpiresInSeconds`. Esto permite:

- Clientes de alta seguridad: tokens cortos (1h)
- Clientes batch: tokens largos (hasta 7 dias)
- Sin necesidad de redeploy para cambiar la duracion

### Refresh token rotation con deteccion de reuse

El refresh token implementa rotation (cada refresh invalida el anterior) y deteccion de reuse attack (si alguien intenta reusar un token ya revocado, se revocan todos los tokens del cliente). Esto sigue las recomendaciones de OWASP para refresh tokens.
