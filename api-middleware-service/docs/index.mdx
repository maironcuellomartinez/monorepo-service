# API Middleware Service

> Proxy OAuth2 para aplicaciones externas hacia Event Corner (api-gateway interno).

---

## Descripcion

`api-middleware-service` es un middleware de autenticacion y autorizacion construido con **NestJS** que actua como intermediario entre aplicaciones externas y un api-gateway interno (Event Corner). Implementa el flujo **OAuth2 client_credentials** con JWT local, gestion de clientes externos con bcrypt, y una capa de resiliencia de 3 niveles.

## Stack tecnologico

| Componente | Tecnologia |
|---|---|
| Runtime | Node.js 20 LTS |
| Framework | NestJS 10 + TypeScript 5 |
| Base de datos | MySQL 8 via TypeORM |
| Autenticacion | JWT local (bcrypt + @nestjs/jwt) |

| Documentacion | Swagger (@nestjs/swagger) |

## Flujo de autenticacion

### 1. Registro de cliente

Un administrador registra la aplicacion externa via `POST /clients`. Se genera:

- `clientId` con prefijo `mc_` (ej: `mc_a1b2c3d4...`)
- `clientSecret` de 32 bytes hex (se muestra una sola vez)
- El secret se almacena como **bcrypt hash**

### 2. Emision de token

La aplicacion externa solicita un token via `POST /oauth/token` con **Basic Auth**:

```
Authorization: Basic base64(client_id:client_secret)
```

Response:

```json
{
  "access_token": "eyJhbGciOiJIUzI1NiIs...",
  "refresh_token": "eyJhbGciOiJIUzI1NiIs...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "client_name": "Mi App"
}
```

### 3. Acceso a datos

La aplicacion externa usa el access token en requests subsecuentes:

```
Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
```

### 4. Refresh token rotation

- El refresh token se almacena como **hash del jti** en la tabla `refresh_tokens`
- Al refrescar, se revoca el token anterior y se emite uno nuevo
- Si se detecta un **reuse attack** (hash no coincide), se revocan TODOS los tokens del cliente

## Capa de resiliencia

### Nivel 1: HTTP Bulkhead entrante

Middleware que limita requests concurrentes entrantes (default: 50 concurrencia, 100 cola). Excluye `/health/status`.

### Nivel 2: OAuth Bulkhead

Guard especifico para `POST /oauth/token` que limita a **3 bcrypt simultaneos** (max 5 en cola, timeout 5s). Protege contra fuerza bruta y DoS via bcrypt.

### Nivel 3: Gateway saliente

- **PQueue**: colas de prioridad separadas (HP: concurrencia 10, LP: concurrencia 5)
- **Circuit Breaker** (opossum): se abre si >50% de errores 5xx en ventana de 5 llamadas, reset a los 30s

## Seguridad

- **Helmet**: protege contra vulnerabilidades HTTP comunes (XSS, clickjacking, etc.)
- **Compression**: respuestas gzip para rendimiento
- **Rate limiting**: global (100 req/min) + especifico por endpoint (token: 10/min, refresh: 5/min, login: 5/min)
- **Bulkhead**: 3 capas de proteccion contra sobrecarga
- **bcrypt**: secrets almacenados con hash, nunca en texto plano
- **Refresh token rotation**: cada refresh invalida el token anterior
- **Reuse attack detection**: si se reusa un refresh token, se revocan todos los tokens del cliente
- **CORS**: origenes explicitos, no wildcard
- **Cookie httpOnly**: sesion de admin con cookie secure + sameSite strict
- **Validacion de entorno**: `requiredSecret()` lanza error si faltan secretos en staging/production

## Decisiones de diseno

| Decision | Opcion elegida | Alternativa descartada |
|---|---|---|
| Autenticacion | JWT local + MySQL | OAuth introspection externa (se descarto por divergencia arquitectonica) |
| Duracion de token | Configurable por cliente (1h-7d) | Fija global |
| Refresh token | Rotation con deteccion de reuse | Sin refresh token |
| Bulkhead OAuth | Implementacion casera con cola | Rate-limit por IP (requiere Redis) |
| Circuit breaker | opossum | Implementacion propia |
| Sesion admin | Cookie httpOnly + JWT | API key fija |
| Documentacion | Swagger en no-prod | Documentacion estatica |
