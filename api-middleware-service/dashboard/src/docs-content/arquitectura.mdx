### Refresh token rotation

El refresh token sigue el esquema de rotation con deteccion de reuse attack recomendado por OWASP. El jti se almacena como hash bcrypt — nunca en texto plano:

<MermaidDiagram chart={`
sequenceDiagram
  autonumber
  actor App as App externa
  participant MW as api-middleware-service
  participant DB as MySQL

  App->>MW: POST /oauth/refresh { refresh_token }
  MW->>MW: jwt.verify(refresh_token) → extrae jti + clientId
  MW->>DB: SELECT token WHERE clientId=? AND revokedAt IS NULL ORDER BY createdAt DESC

  alt Token valido (bcrypt.compare pasa)
    MW->>DB: UPDATE token SET revokedAt = NOW()
    MW->>DB: INSERT nuevo refresh_token (bcrypt del nuevo jti)
    MW-->>App: nuevo access_token + nuevo refresh_token
  else Token no encontrado o ya revocado (reuse attack)
    MW->>DB: UPDATE ALL tokens SET revokedAt = NOW() WHERE clientId=?
    MW-->>App: 401 Unauthorized
    Note over App,DB: Todos los tokens del cliente son revocados
  else Token expirado
    MW-->>App: 401 Token expired
  end
`} />

## Decisiones arquitectonicas

### Autenticacion local vs OAuth externo

Se eligio **JWT local + MySQL** sobre OAuth introspection externa porque:

- Sin dependencias de red adicionales — la verificacion es local, no requiere round-trip HTTP en cada request
- Latencia menor y predecible — verificacion de JWT en microsegundos vs llamada HTTP externa
- Control total sobre el ciclo de vida de los tokens — rotacion, revocacion y expiracion por cliente

### Duracion configurable del token por cliente

Cada cliente tiene su propia duracion de access token (entre 1h y 7 dias), almacenada en `tokenExpiresInSeconds`. Esto permite:

- Clientes de alta seguridad: tokens cortos de 1 hora
- Integraciones batch o long-running: tokens de hasta 7 dias
- Cambio de duracion en caliente desde el dashboard — sin redeploy

### Refresh token fijo vs configurable

El refresh token tiene duracion fija de **7 dias** para todos los clientes. Esta decision es deliberada: en un flujo `client_credentials`, las aplicaciones server-side ya tienen su `client_secret` almacenado y pueden re-autenticarse directamente en cualquier momento. Un valor fijo es suficiente y elimina una variable de configuracion innecesaria.

| Decision | Opcion elegida | Alternativa descartada |
|---|---|---|
| Autenticacion | JWT local + MySQL | OAuth introspection externa |
| Duracion de token | Configurable por cliente (1h–7d) | Fija global |
| Refresh token | Rotation con deteccion de reuse | Sin refresh token |
| Duracion refresh token | Fija 7 dias para todos los clientes | Configurable por cliente |
| Bulkhead OAuth | Implementacion casera con cola | Rate-limit por IP (requiere Redis) |
| Circuit breaker | opossum | Implementacion propia |
| Sesion admin | Cookie httpOnly + JWT | API key fija |
